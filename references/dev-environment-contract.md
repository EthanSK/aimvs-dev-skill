# Developer environment contract

Read before any AIMVS local dev-environment, dev-stack, emulator, or fixture operation, or adding, changing, or reviewing dev-only tooling, fixtures, or production code supporting them.

- Stack 0's shared emulator data belongs to Ethan's main VS Code environment. Every nonzero dev stack must use its own isolated Firebase, Storage, MinIO, and Download Assets Worker backend; never point it at stack 0's backend or mutate shared data for an agent test. Never delete, clear, replace, anonymize, rename, or mark removed any pre-existing shared-emulator document to manufacture an empty or recovery state. Never restart the shared emulators from a worktree export until its source and representative collection counts have been verified against the currently owned full dataset.
- Before manually stopping or restarting any AIMVS Firebase emulator backend, export and verify its current data once. Use `npm run export-emulator-data` only for stack 0's shared backend. For every nonzero stack, stop its native writers first, then use the guarded `npm run isolated-backend -- stop --dev-stack-index=N` command so its private data is exported and its private containers stop cleanly. Do not run a periodic background exporter outside stack 0.
- If I tell you to use the Firestore emulator from Node/Admin SDK scripts, use the real standalone API project id selected by `.firebaserc`'s `development` alias (`vibideo-ai-staging` after the local migration), not a Firebase CLI alias; the emulator stores separate namespaces per project id, and using the alias patches the wrong data. Local `firebase` CLI commands use `--project development`; hosted projects need their explicit project ID, because `.firebaserc` keeps no other alias. Never add a one-shot migration, rebuild, repair, or backfill script—or a `package.json` command that invokes one—to any repository path, even temporarily or untracked. Create it only in a task-owned temporary directory outside the repository, execute and verify it with the required authorization, then delete it before handoff; retain tooling only when Ethan explicitly asks for a reusable permanent command.
- Stack 0 is my main VS Code environment. Agents must never start, stop, restart, restore, or use stack 0 for their own tests unless I explicitly ask for that exact stack 0 action. Asking to fix dev stack 0 authorizes restarting only its affected process after checking ownership; a shared Firebase backend restart still requires the verified one-shot export above. It does not authorize agent tests or unrelated restarts. Read-only port and log inspection is allowed. User clarification — 2026-09-29.
- Manual browser tests remain opt-in: run them only when I explicitly ask in the current task. When the task includes a planned manual app check that needs AIMVS running, start or reuse the exact task-owned nonzero dev stack before handoff and leave it running for me, even if I did not separately ask you to start it. Do not boot a stack merely because its number is reserved or when no live manual check is needed. Follow `$aimvs-dev` for every local browser test or dev-stack run; every agent-run test that accesses a runtime uses a nonzero stack index with `--dev-stack-index=N`, even when testing source from the main checkout. Pure unit tests using local doubles need no running stack. Self-improved — 2026-10-28: distinguish pure unit checks from runtime tests (Codex task: `01a17f2e-00a9-75a1-9365-dcd025a5e32c`). ## Performance over time

- When the current checkout has the Fleet adapter and The Fleet resolves it to a registered project, send finite development builds and checks through it: existing `build:frontend:dev`, `build:api:dev` and configured npm check scripts, or `npm run fleet -- nx <finite arguments>`. Keep the small frontend server, manual API/emulators and existing editor setup local. Use Nx affected selection and caching, not a separately maintained dependency cache. A busy/failed worker must surface; Ethan deferred overload monitoring and automatic local fallback. Read `tools/scripts/dev-stack/FLEET.md` in that checkout for setup, current commands, return and recovery. The committed `the-fleet.json` owns AIMVS recipes; the installed `the-fleet` CLI and private `~/.the-fleet` controller settings own registrations, machine order and returned-results storage. Resolve and submit the current worktree's own recipe/source, including uncommitted changes; never use the registered main checkout as its substitute or recreate `.git/aimvs-fleet.json`. A missing CLI or unregistered checkout stays local; an installed controller error must surface. A checkout without the adapter keeps its existing workflow; do not assume an instruction commit installed executable tooling. User-requested — 2026-11-01 (Codex task: `01a19409-9c61-7a93-9d9c-ee26b3432774`).
- Development E2E authoring and iteration use an eligible worker selected by The Fleet via `npm run e2e -- <native selection>`. Keep the whole test stack there, return passing and failed reports, and verify ownership-checked cleanup of processes, containers and ephemeral data. Bounded reusable setup caches are separate from per-run data. Choose whether a cloud landing check is needed using [aimvs-e2e's landing decision](../../aimvs-e2e/SKILL.md#choose-whether-a-cloud-landing-run-is-needed); smaller, predictable changes can rely on relevant passing Fleet checks. Do not silently replace an unavailable configured worker with a local or paid cloud run. User-requested — 2026-11-01 (same task).

- Assess dev-stack and setup changes during implementation and review for performance after hours or days of idle and repeated use, including several stacks running together. Consider CPU, memory/swap, disk/network activity and anything that accumulates: processes, workers, listeners, timers, polling, retries, logs or caches. Check what remains running after a browser page, test, launcher or owning stack stops.
- Consult relevant recent Git/task history and the current owning code before choosing or approving the change. Reuse the established fixes and constraints rather than rediscovering or undoing them. Start with the existing [emulator leak and idle-worker lessons](emulator-safety.md#leaked-webchannel-sessions-and-idle-functions-workers), [host memory lessons](emulator-safety.md#host-memory-and-swap-contention), [stack lifecycle](stack-lifecycle.md) and, when reports are involved, the report-viewer lifecycle in `z-e2e/src/tools/show-report.ts` and `$aimvs-e2e`. Follow those sources as they evolve; do not maintain another incident list here.
- Before handoff, briefly state the likely sustained/accumulating load, which relevant past fix was checked, and the evidence or remaining uncertainty. A clean startup or short passing test does not prove long-running performance. Choose proportionate, bounded validation; this check does not authorize browser tests, stopping another task's processes or changing retention rules.

User-requested — 2026-10-24: consider performance issues with dev-stack/setup changes after things have been running for a while, and look at how recent problems were fixed to prevent them happening again.

## Dev-only code and fixtures

- For published-video playback, seeking, frame stepping, or aspect-ratio checks, create fresh videos through the current Published Videos dev action using the bundled one-minute moving `dev-test-*.mp4` clips. Existing published fixtures retain their copied footage after a rebuild or rebase; do not use the old one-second “Music Video Goes Here” clips or Project empty-preview placeholders for these checks. Verify the new video's duration, media filename, and visible movement before testing. User request — 2026-10-08.
- Never add or retain production code solely for dev tooling or fixtures. Developer stuff must work around normal production behaviour, not change fundamental code or make normal startup slower to accommodate an artificial reset state. Before finishing a dev reset, check that its stored state and browser selections satisfy existing production assumptions and remove any production workaround added solely for that reset. Keep dev-only response fields, helpers, and behavior in dev-only modules, and keep fixture generation and dev-only orchestration in `*.dev.*` files; normal services expose only reusable domain operations required by production callers, never `ForDev` entry points.
- Browser-visible dev fixture rows must not have exactly equal Added dates or other same-field sort dates within one list. Capture one date anchor per batch and assign deterministic, distinct `Timestamp` values per row; do not rely on server timestamps, write timing, sleeps or random offsets. Keep spacing at least one microsecond because Firestore rounds away smaller differences. Preserve lifecycle order and derive date buckets from the assigned dates. Before finishing, verify distinct dates under a frozen clock and after storage precision is applied; when manual testing is requested, switch ascending/descending sort on the fixture list. Equal fields belonging to the same event and deliberate unit-test tie cases remain valid. User request — 2026-10-05.
